## Classify and plan

| Class | Choose when | Planning |
|---|---|---|
| Simple (default) | Understood fixes, presentation/content adjustments, isolated helpers/features and ordinary docs/tooling changes | A brief approach and observable acceptance criteria in chat; no saved plan |
| Complex | A named save/schema migration, changed shared contract, new persistent subsystem, consequential release-gate change, or unresolved design decision with a concrete failure risk | A saved plan in `game/docs/plans/YYYY-MM-DD-topic.md` with acceptance criteria, milestones, applicable verification and release status |

State the class and reason early. Default to simple unless evidence establishes a consequential risk or unresolved design choice; name that risk when choosing complex. Adding a module, calling existing connected systems, changing several files, or needing browser tests does not itself qualify. An isolated new feature can be simple. Casey's override takes effect immediately. Upgrade only when investigation establishes a wider risk. Planning complexity and verification scope are independent decisions. Keep the solution within scope. Plans record actual progress and evidence, including unresolved failures. This document owns detailed workflow commands and release policy; other instructions summarize and link here.

## Choose checks by impact

| Changed behavior | Required checks | Release |
|---|---|---|
| Documentation or Codex instructions | Review wording, consistency and `git diff --check` | No game build, tests, screenshots or deployment |
| Developer tooling or CI configuration | Focused tests or configuration checks for the affected automation; broaden for concrete integration risk | No manual game deployment unless published output changes; existing CI may still execute on an automation change |
| Game code, player assets, runtime dependencies or built game output | Meaningful regressions and `npm run verify`; relevant browser tests and visual inspection | Automatic deployment and exact live commit/HTML verification |

A simple gameplay fix can need browser testing. A complex documentation change can need no executable tests. Do not add tests that merely repeat prose or run unrelated suites to satisfy a task label. Stop verification when the required checks pass unless new changes or unresolved evidence justify more. Markdown-only pushes are excluded from the Pages workflow; mixed changes retain their normal checks.

## Develop and verify

1. Inspect git status before editing and preserve unrelated work. For game implementation, read root `AGENTS.md`, project instructions, architecture and required topic docs. For documentation/Codex rule edits, read the affected instructions and relevant workflow sections; reuse context already read and avoid unrelated game-system investigation.
2. Establish the behavior that must change and how it will be checked. Implement in manageable stages; run focused checks during development. Add regression coverage where it verifies behavior or a meaningful failure mode. Pure wording changes need no mirrored unit test.
3. When executable checks need dependencies, use the locked dependencies; run `npm ci` when installation is needed. On a new machine run `npm run test:install` only when UI checks are needed (Linux also installs browser system dependencies).
4. Use tiered verification for game changes. During development run `npm run verify -- --defer-ui` for core/build checks and select focused browser cases with `npm run test:ui -- --suites=music,sound --project=phone-webkit` (example). The local runner always adds smoke; omit `--project` to exercise all three browsers. `npm run verify` runs the automatically selected suites locally; `npm run verify -- --ui` explicitly runs the full suite. Do not repeat a passing unchanged full local suite and full CI merely for another green command. CI is the authoritative exact-commit release gate. CI verifies the published commit and HTML, then unions changes since that publication with the push/PR diff for coverage. This retains unpublished game changes after a failed rollout. Automatic publication eligibility uses only the live-to-candidate game/dependency/packaging delta; reverts and test-only changes do not republish unchanged output. Missing Git comparison evidence selects full coverage; inability to verify the live baseline blocks publishing workflows early rather than guessing. The receipt in ignored `work/test-selection.json` records tier, suites, core requirement, publication flag, reason and available changed paths. `--defer-ui` cannot override explicit `--ui`.
   - **Focused:** short smoke (creation, real SQL, navigation, export/import/reload, title/town layout) plus affected named suites, on phone Chromium/WebKit and desktop. Reviewed families cover audio/music, effects, actor appearance, building presentation, query/editor feedback, venue games and presentation-only landscape modules and landscape/architecture/cartography atlases. Landscape mapping covers its NPC/building/map consumers; physical world generation, movement and saves remain full. `test/select-tests.js` owns explicit mappings; `test/ui-suites.js` owns inventory/dependencies. Extend mappings only after reviewing consumers and adding selection regressions; never guess that an unknown path is safe.
   - **Journeys:** `npm run test:ui -- --suites=journeys` includes `first-day` and all four complete profession days. Focused `first-day` runs retain its targeted regressions without those four long cases. Editing their owning fixture selects journeys automatically. Nightly and explicit full checks always retain them. Relevant progression, arrival, movement and shared-game changes still select full; a focused change cannot evade a known relevant failure. The separate `test:paths`/`test:dungeons` extended campaigns remain opt-in for relevant progression/balance/expedition work.
   - **Full:** shared gameplay, saves/world ownership, progression/arrival, movement (including `actor_rig.js`, which supplies physical walking/running speeds), offline storage, global layout/shell, packaging/runtime dependencies, unknown game files and shared browser fixtures. Retains every existing browser case, including `journeys` and dungeon components. An incomplete full inventory fails the release gate. Simple planning never overrides this risk selection.
   - **Tooling:** `npm run test:protocol` verifies selection, real test discovery and publication gates. Runner/registration changes also exercise short browser coverage; other changed pure tests still require core assertions. Browser-only repairs select their suite plus smoke; shared-fixture changes select full. Test-only/tooling changes do not deploy the unchanged game. Game packaging changes conservatively require full checks, including offline packaging; HTML equality alone cannot establish release equivalence.
   - Keep selected failures mandatory until repaired. Never reclassify a failing change to evade a required test. Scheduled failures must be triaged before an affected release. Preserve deterministic prepared UI transactions; seed relevant combat outcomes locally and restore the original RNG in `finally`. Test probability/risk separately with pure rules and intentional balance runs; never tune production stats or add broad retries to stabilize a UI fixture.
5. Browser tests cover phone Chromium, phone WebKit (390×720), and desktop Chromium (1280×800). They exercise character creation, navigation, SQL execution, save-code export/import, and persistence; the localhost fixture captures title, town, fight, bag, paper doll, dungeon, dojo, and interior scenes. Each test uses isolated browser storage. The fixture and debug controls are never deployed.
6. For UI, rendering, art, or layout changes, add targeted interaction assertions and open the affected screenshots in `game/test-results/`. Inspect readability, clipping, touch controls, asset placement, and the intended behavior. Captured screenshots are evidence for human/agent review, not pixel-difference approval. Never bless new screenshot baselines to conceal a defect. Real-device audio, performance, and iPhone keyboard behavior require real-device evidence when relevant.
7. Review the diff and acceptance criteria. Update the owning master doc and dated Decision log only when documented behavior, a lasting decision or a current/planned description changes. A fix restoring documented behavior needs no master-doc churn or saved plan. Fix failures and rerun affected checks. Do not ship with a required check skipped or unresolved. If tools or external access prevent verification, say exactly what is blocked rather than reporting success.

## Commit and deploy automatically

- Concurrent tasks develop in isolated worktrees with separate local ports and outputs. Assign one publisher at a time for the shared live game; other tasks continue implementation or bounded review. Before the next release gate, integrate the preceding publisher's verified source and documentation closure, resolve shared-file changes deliberately, and preserve all earlier fixes. The existing concurrency group and live-baseline guard do not coordinate Git merges or task ownership. Avoid duplicate repair owners, competing publications, cancelling another task's runs and repeated status polling. The [2026-11-25 coordination plan](plans/2026-11-25-parallel-release-coordination.md) records the current three-task assignments and release order.

- Stage only the task's intended files. Keep raw art, build output, browser binaries, reports, credentials, and temporary files out of git. Never commit another task's edits accidentally.
- If Casey requests local-only work or says not to deploy, leave edits uncommitted and do not push or dispatch a workflow. A push can trigger deployment even when no manual deploy command is used.
- Otherwise commit with a concrete description. Push the checked commit to `main` with `git push origin main`. Markdown-only changes do not trigger Pages and need no live verification. For game releases, if working on another branch, integrate normally and reverify the resulting main; do not force-push or overwrite remote work. If the remote advanced, fetch, integrate safely, and rerun applicable checks on the result.
- GitHub Actions first computes a validated plan. Actual game changes run core `npm run verify -- --defer-ui`; protocol-only changes run `npm run test:protocol` and build only if browser execution needs it. Three required profile jobs run the same selected suite list with zero retries and fail-fast disabled. The stable `build` aggregate rejects missing/malformed plans, incomplete full inventories and failed/cancelled/skipped selected browser jobs. Pages upload requires a real publication delta. The main-only deployment job requires successful selected checks and an uncancelled run. Its fresh live-baseline check rejects stale/divergent candidates and any changed baseline since verification; rerun all jobs after such a change. An exact candidate already live is checked through the hosted flows without republishing. CI uses canonical Node invocations for verification/build/live checks, so package script aliases cannot make tested and published artifacts diverge. No browser-test/tooling-only push republishes the game.
- Every day at 09:20 UTC, scheduled full coverage runs without publishing. Its concurrency group is separate from releases so a long nightly cannot queue-block a small deployment. Manual `scope=full` validation also defaults to no publication; `scope=smoke` is validation only. Manual publication requires `scope=full`, `publish=true` and main. Normal game pushes keep automatic publication after their selected gates.
- The canonical build writes `dist/release.json` with the source commit and built HTML SHA-256. After Pages deployment, CI verifies both and exercises the real hosted game without replacing SQL or using local debug handles. Hosted smoke always checks real SQL/navigation/save round-trip. A validated focused plan adds affected audio, battle and arrival flows; asset changes also require the complete offline download/reopen/restore flow. Full/risky plans retain all six hosted cases. Missing standalone scope defaults to all flows and malformed scope fails closed. `test/live-suites.js` owns this mapping. Tooling-only changes do not publish or run hosted flows against an unchanged release.
- Monitor the run for the pushed SHA, for example `gh run list --workflow pages.yml --commit <sha>` and `gh run view <run-id>`. A green build alone is not a verified deployment; the deployment and live-check steps must pass too.
- CI is the authoritative exact-commit release gate. Do not repeat passing unchanged local full or hosted checks without a concrete unresolved concern. If CI already verifies the live identity and required player flows, reuse that evidence and inspect its relevant screenshots. For an independent check when needed, set `BW_BASE_URL=https://caseyschindler123.github.io/Brasswake/`, `BW_EXPECT_COMMIT=<full-sha>` and optionally `BW_LIVE_UI=true`, then run `npm run test:live` from `game/`. Standalone UI checks default to all hosted flows; clear task-specific environment variables afterward.
- If validation fails, repair the change and rerun checks before pushing a correction. If deployment or live verification fails, inspect the failing step, repair and redeploy, and verify the new SHA. Do not call it done or blindly retry permanent failures. Any emergency rollback must preserve git history and be verified as a separate release.

## Completion report

Report the task class, outcome, checks actually run, visual evidence when applicable, commit SHA or local-only status, deployment status when applicable, a concise cost summary, and material limitations. A documentation-only task has no game-release gate.

After successful game deployment/live verification, record concise evidence in `game/docs/RELEASE_HISTORY.md`: released SHA, Actions link, verification date/timezone, available HTML hash, checks passed and limitations. Close/link a plan only when one exists. Avoid repeating the release narrative across master docs; update affected current-state descriptions and lasting decisions. Tooling-only work records its checks and non-publication status in its plan or completion report. Distinguish historical failures/checkpoints from current evidence; missing evidence stays unavailable.

Ignored `work/` receipts, logs and screenshots are supplementary; they must never be the only record of release completion. Review affected master summaries and planned sections for contradictions before ending the task. Closure is a documentation-only change: it does not require another game test/build/deployment or rewriting the released commit. Commit/push documentation normally when authorized; under a local-only/no-deploy hold, leave it uncommitted and say so. Review enforces prose consistency; CI does not automatically verify the meaning of decisions or summaries.

Every completion message includes costs for that task/release: main AI, delegated AI, paid tools and CI/deployment. Use existing task-specific usage/billing evidence, label amounts measured or estimated, and identify the source. If unavailable, say so; never turn unknown data into $0 or present a partial subtotal as a complete total. Confirmed absence of agent/tool activity can be reported as no usage. Fixed subscription allocation is separate from incremental charges. Account-wide usage percentages and elapsed time cannot establish a per-task dollar cost.

Prefer one task per chat. For multiple releases in one chat, use task-specific usage deltas when available; otherwise say attribution is unavailable. Identify the commit/run when there is a release and say no deployment for local-only work. This is a reporting rule: do not build collectors, maintain ledgers, install plugins or request billing access unless Casey asks. Keep private billing information out of git.

## Delegation and cost

The main agent owns classification, acceptance criteria, task decomposition, integration, and release. Use the delegation rules in root `AGENTS.md`: default to one agent, delegate only bounded independent work with a clear expected benefit, select the least expensive suitable available model and reasoning effort, and escalate capability when the evidence warrants it. Avoid duplicate reading, overlapping edits, recursive delegation, unnecessary screenshots, and repeated unchanged test runs. Prefer narrow worker context and concise deliverables. Exact costs depend on the available product/model; do not invent a price or promised savings.
